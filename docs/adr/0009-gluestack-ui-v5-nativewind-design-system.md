# gluestack-ui v5 + NativeWind v5 for the UI/design system layer

We're replacing the app's ad hoc per-screen `StyleSheet.create` styling (all six screens plus the `App.tsx` chrome) with gluestack-ui v5 as the component library, paired with a real design system: a custom cockpit-inspired palette (deep navy base, amber accent — exact values pending), the existing red/amber/green Verdict colors promoted to semantic theme tokens, a type scale, a spacing scale, and a minimal icon set (`lucide-react-native`). This is a full redesign, not a like-for-like component swap. gluestack was chosen over hand-rolling a design system because building one from scratch for six screens (and future ones) is more work than adopting one, and its copy-paste (shadcn-style) component model keeps the code owned in-repo rather than pulled in as an opaque npm dependency.

The styling engine is **NativeWind v5**, the only option gluestack-ui v5 supports on a bare React Native CLI project (UniWind, its alternative, is Expo-only). NativeWind v5 is currently a preview release (`nativewind@^5.0.0-preview.2`), pinned to exact versions rather than waiting for GA or starting on the stable gluestack-ui v4 / NativeWind v4 line instead. We're accepting the preview-package risk because this is a personal-scale app with no SLA, and building on v4 now just to re-migrate to v5 later would double the work.

This pulls in new native dependencies — `react-native-reanimated` + `react-native-worklets`, `react-native-svg`, and a pinned native binary `lightningcss@1.30.1` — requiring `pod install`/Gradle rebuilds. That sits next to ADR 0004's F-Droid/reproducible-build commitment and ADR 0001's bare-RN-CLI-over-Expo stance, but none of these are proprietary or cloud-dependent (the actual concern behind those ADRs) — they're OSS, npm-distributed, and built from source. The gluestack skill's setup docs are written Expo-first (`expo/metro-config`, `npx expo run:*`, `npx expo install --fix`); we're translating those to bare-RN-CLI equivalents (`@react-native/metro-config`, `pod install` + `react-native run-ios`/`run-android`, manual dependency installs) rather than following them literally, consistent with ADR 0001.

## Consequences

- NativeWind v5 being pre-release means breaking changes are possible before it reaches GA; a NativeWind version bump mid-rollout may require rework across already-migrated screens.
- Palette direction is decided (cockpit-inspired navy + amber, over a sky-blue-continuity or high-contrast-neutral alternative) but exact hex values are still pending — theme token names/structure ship ahead of final values.
- Dark mode is a manual, explicit in-app toggle for preserving night vision on pre-dawn/dusk flight checks, not an automatic follow-system-appearance feature. Don't "simplify" it to auto-follow OS theme without revisiting this reasoning — the use case is night vision, not aesthetic preference.
- A custom app icon is explicitly out of scope here; the app still ships React Native CLI's default placeholder icon. Treat as a separate follow-up once the palette is finalized.
- If gluestack-ui v5/NativeWind v5 is ever abandoned for v4 or a hand-rolled approach, that should come with an ADR explicitly superseding this one, not an incidental dependency rollback.
